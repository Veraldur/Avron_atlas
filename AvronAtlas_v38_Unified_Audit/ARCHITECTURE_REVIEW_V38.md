# AvronAtlas v38 — архитектурная ревизия, карта кода и план развития

**Дата:** 3 ноября 2026. **Область:** текущий офлайн-проект AvronAtlas/Aether Studio, `src/`, `pantheon/`, два предоставленных ZIP-архива Foundry Avron 1.33. **Статус:** реализованный интеграционный слой, аудит связей и изолированное браузерное тестирование. Это НЕ подтверждение полного ручного QA всех экранов с работающим Phaser.

## 1. Решение: единый реестр, но не одна гигантская таблица

**Источник истины — JSON мира `S.world`; ID неизменяемый.** Каждая сущность хранится **один раз** в своей доменной коллекции. Унифицированные `kind:id`-ссылки позволяют связать любые компоненты без копирования. Экспонат — *проекция* исходного объекта в витрине (`showcaseId~sourceKind~sourceId`), а не самостоятельный дубликат. Реестр читает коллекции и строит сводный индекс; движки остаются интерфейсными адаптерами.

```
             Создать / изменить / связать / удалить
        карта · Finder · Летопись · Пантеон · витрина
                             │
                AvronMaterials (v38)
                  │     │       │
               CRUD   граф    аудит / миграция
                  │     │       │
             AvronRegistry (v37)
                  │
            S.world (JSON мира)
     ┌─────────┬──────────┬─────────┬──────────┐
   articles  entities  chronicles  showcases  loreMatrix ...
                  │
      IndexedDB + экспорт/импорт JSON
                  │
          AvronNav (v30): ОТКРЫТЬ ПО ID
                  │
            UI адаптеры движков
```

Контракты: `AvronMaterials.create(kind, opts)`, `adopt(kind, originalObject)` (не теряет геометрию/метаданные), `attach(from,to)`, `detach(from,to)`, `relate(fromEntity,toEntity,typeId)`, `remove(ref)`, `graph()`, `audit()`, `titleLookup(name)`, `scanWiki()` и `indexExplicitWiki()`. `AvronRegistry.all()` — сводный индекс, `item('article:...')` — исходная запись, `createDialog()` — универсальное создание статьи с несколькими родителями. Навигационный контракт `AvronNav.open('article:ID')` / `AvronNav.open({kind,id})`.

### Почему нельзя использовать заголовок как ID

В архиве есть повторяющиеся названия. Заголовок может быть исправлен или переведён, но постоянный ID материала остаётся. Finder ищет по заголовку и псевдонимам, **не открывает произвольную первую запись, если найдено несколько совпадений**. Явные ссылки `[[Название]]` конвертируются только при однозначном совпадении; сомнительные отправляются в отчёт.

### Отличия типов связей

- `article.parentRefs` + `contentLinks` — материнство, привязка, обратные переходы в редакторах.
- `world.relations` — семантические отношения **между объектами карты**, с `typeId`. Новый `AvronMaterials.relate()` сохраняет именно этот формат, а `graph()` включает его в единый читаемый граф.
- `book.articleIds`, `lore.articleId`, `entity.articleId`, `god.articleId` — прежние foreign-key поля; унифицированные методы синхронизируют их с `contentLinks` при основных действиях.
- `[[Название]]` — текстовое упоминание/цитата, не материнство. `AvronMaterials.indexExplicitWiki()` материализует поисковый переход и не переписывает `parentRefs`.
- `showcase.order` — расположение/видимость экспонатов в витрине, а не новый самостоятельный объект.

## 2. Контроль данных и миграция Аврона 1.33

Два предоставленных архива содержали **885 Markdown-документов**: **603** в JournalDirectory и **282** в «Книги». Данные импортированы как статьи в собственных разделах библиотеки; исходные пути и `foundryId` сохранены в `sourcePath`/`foundryId`, категории вложенности — в `world.folders`. 174 графических файла вложены как локальные `assets/import-v38/*` по SHA-имени. Markdown ссылается на эти файлы относительными путями, не через сеть.

Количество статей: **26 исходных v37 + 885 импортированных + 1 технический тест = 912**. **Все 266 исходных объектов карты сохранены.** Из архивных ссылок построены 102 новых явных перехода и 20 точных соответствий объект карты → статья. **11 wiki-целей не разрешены, 1 неоднозначна**: см. `reports/UNRESOLVED_FOUNDRY_LINKS_V38.json`; они не были подменены искусственными совпадениями.

Технический маршрут (не канон): `book:av38-test-chronicle → article:av38-test-chronicle-article → lore:av38-test-intersection → entity:b5823692 (Амена)`, плюс Цитадель Вечного Света. Книга, сцена и статья отмечены как технические/черновые/не опубликованные. Редактор может удалить их после проверки.

**Предупреждение о совместимости:** сохранённый мир в IndexedDB имеет приоритет над встроенным примером. Чтобы не потерять авторские правки, открой сохранённый Аврон → `⚙ Файлы` → **«Добавить архивы Аврона 1.33 (без замены)»** → экспортируй JSON. Импорт добавляет только отсутствующие записи по стабильным ID, не заменяет текст существующих статей и идемпотентен. `Аврон` в стартовом меню — это *чистая копия актуальной встроенной версии*, которая заменяет текущий мир с подтверждением.

## 3. Весь рабочий поток

1. Пользователь нажимает «＋ Статья» в Хранилище/объекте/Летописи/части Пантеона; движок вызывает `AvronMaterials.create('article',{title,parents:[...]})` либо диалог `AvronRegistry.createDialog()`.
2. Движок карты при рисовании многоугольника вызывает `AvronMaterials.adopt('entity',e)`; полная геометрия не упрощается; авторская метаинформация остаётся в исходной записи.
3. После подтверждения материнства `attach` создаёт один реальный `contentLinks` и обновляет `parentRefs`, а для Летописи/пересечения — `articleIds`/`articleId`.
4. `AvronMaterials.changed()` помечает мир изменённым, вызывает отложенную запись и инвалидирует индекс Finder. Нельзя считать «написано в массив» подтверждением сохранения на диск.
5. `AvronPersistence.save()` сохраняет JSON-снимок в IndexedDB транзакцией с уведомлением об ошибке; `Экспорт JSON` создаёт переносимый резервный файл.
6. Навигатор разрешает ссылку по `kind:id`, открывает канонический движок, история v31 сохраняет предыдущие переходы; статьи в редакторе открывает `AvronArticleStudio`.
7. Удаление через `AvronMaterials.remove(ref)` удаляет запись и очищает **типизированные** обратные связи, не удаляя случайно дочерние страницы и другие узлы.

## 5. Ревизия качества: выявленные проблемы и приоритет

### P0: сохранение, источник мира, открытие статьи — исправления v38

- «Открыть статью» в пересечении: теперь вызывает `AvronNav.open('article:'+id)`, в редакторе при отсутствии цели предлагает создать привязанную статью.
- Устаревший встроенный JSON: реальный файл `src/default-world-current.js`, используемый `index.html`, заменён новой версией (раньше обновлялся только `default-world-v32.js`).
- Старые кнопки создания часто писали напрямую в массив; основные пути перенаправлены на единый интерфейс v38.
- Устаревшая ссылка на статью из Хронологии была через `switchScreen`; заменена общим навигатором.
- Миграция работает без стирания пользовательского текста и с контролем повторного применения.

### P1: недоработки, требующие следующего рефакторинга

1. **Два уровня мутаций:** `AvronRegistry.setParents()` и `AvronMaterials.attach()` ещё сосуществуют. Все UI-формы родительских связей желательно окончательно перевести на одни функции, уменьшив риск рассинхронизации foreign keys.
2. **Команды редактора должны быть транзакционными:** `create` сейчас сохраняет несколько массивов последовательно; полный rollback при исключении пока отсутствует. Для крупной базы нужен один `WorldRepository.transact()` с атомарным commit в IndexedDB.
3. **История навигации v31** оборачивает существующие публичные методы, но не знает о каждом старом внутреннем открытии окна; повторные всплытия и z-index требуют живой ручной проверки.
4. **Уникальность `kind:id`:** на будущее валидировать ID до миграции, а не после; создание по одинаковому заголовку запрещено объединять автоматически.
5. **Проекции экспонатов:** их составные ключи меняются при перемещении/удалении исходного материала/витрины. Потребуется стабильный `exhibitPlacementId`, если на экспонат будут навешиваться самостоятельные аннотации.
6. **Прямые поля `entity.articleId`, `lore.articleId`, `chronicle.articleIds`** исторически single/array; они остаются для совместимости. Необходимо либо объявить их производными, либо поддерживать всегда в едином transaction.
7. **Редактор `pantheon/editor.js`, отдельные календарные/типовые кнопки, старые скрытые сценарии** ещё не покрыты интеграционными тестами полного UI. Их нельзя заявлять как полностью исправленные.
8. **Иллюстрации как assets:** в ZIP всё работает по локальным относительным путям, однако одиночного JSON недостаточно для переноса бинарных картинок. Нужен самодостаточный `WorldPackage.zip` с manifest и asset map.
9. **Объём UI:** Finder индексирует много материалов и частично кеширует. На тысячах объектов понадобится инкрементальный индекс или worker, виртуализация длинных списков.
10. **Безопасность Markdown:** импортированные материалы могут содержать внешние URL, HTML и ссылки Foundry; перед публичным просмотром нужен отдельный sanitization/URL-policy прогон.
11. **Версионирование:** world/schemaVersion ещё не покрывает формальные up/down migrations для авторских правок. Следующая ветка — `migration-v39` со снимками версии.
12. **Зависимость от редакторских shortcut:** некоторые `create` без режима Редактор возвращают null; UI должен объяснять почему и не оставлять видимые неактивные кнопки в режиме Просмотр.

### P2: целевая архитектура после стабилизации

`WorldRepository` (единая транзакционная запись) + `MaterialService` (CRUD, types, schema validation) + `GraphIndex` (relations, parent/child, crossrefs, citations) + `ContentIndexer` (Finder and full-text, duplicate titles) + `ViewRouter` (history and overlays) + `ImportService` (Foundry/JSON/ZIP, preview, conflicts, attachments) + адаптеры движков (Phaser, showcase, city, Pantheon, Chronicle) + `DraftWorkspace` (вопросы/ИИ независимо от канона). **React не обязателен, пока инварианты и сохранение не стабилизированы.** Текущий v38 — промежуточная реализация этого разделения без смены фреймворка.
